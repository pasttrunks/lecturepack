<objective>
Fix the slide-sensitivity lock gap (D-08) and verify the Paste Link wiring (D-09). The
sensitivity control on the Process screen is currently locked only during the guided demo,
not during normal processing — a user can click a different preset while transcribing, see
it show "active", but the already-running job ignores the change because its preset was
snapshotted at start_processing() time. The fix extends the lock to cover normal processing.
Separately, the Paste Link / yt-dlp wiring is already fully connected end-to-end in current
code (RESEARCH.md Q5); this plan verifies it works and writes regression tests.

Purpose: D-08 prevents a misleading UX where the user changes a setting that appears to
take effect but does not. D-09 reconnects the Paste Link feature for real URL imports.
Both are independent of the job lifecycle work in Plan 02.

Output: An app.js fix for the sensitivity lock, plus regression tests for both the lock
and the Paste Link wiring.
</objective>

<task type="auto">
  <name>Task 1: Lock slide sensitivity during normal processing</name>
  <files>app/ui/app.js</files>
  <action>
  The current guidedDemoSensitivityLocked() at app.js:2695-2697 returns true only when the
  guided tour is active and the demo flow is not idle. This must also return true (or an
  equivalent sibling check must be added) when a normal (non-demo) job is actively
  processing, per D-08.

  The JS side already receives pipeline_changed signals (line 4090) which populate
  LP.data.pipeline with title, stages, and log. The pipeline_changed handler fires only for
  normal jobs (demo signals are filtered by _forward_normal on the Python side). Use this
  to track a "normal pipeline active" flag.

  Implementation approach: add a boolean to LP.state (e.g. LP.state.pipelineRunning, initial
  value false). Set it to true inside the pipeline_changed handler (line 4090-4097) when the
  payload contains stages with at least one stage whose state is not "complete" and not
  absent. Clear it to false when pipeline_completed or pipeline_failed fires (find these
  handlers by grepping for those signal names in the lpBridge.on registrations). Then extend
  the locked computation in renderSlideDetectionPreset (line 2701) from:
    var locked = guidedDemoSensitivityLocked();
  to:
    var locked = guidedDemoSensitivityLocked() || LP.state.pipelineRunning;

  Also extend setSlideDetectionPreset (line 2716-2721): the existing early return at line
  2717 checks guidedDemoSensitivityLocked(). Change it to check the same combined condition
  (guidedDemoSensitivityLocked() || LP.state.pipelineRunning) so clicking a locked button
  truly no-ops, not just visually disables it.

  Verify that output mode has no UI control on the Process screen. The research (Q6)
  confirmed this: the onboarding overlay buttons set LP.state.onbMode once, then
  start_processing reads it once. There is no Process-screen control to change output mode
  mid-run, so D-08 is already satisfied for output mode by omission. Add a brief code
  comment near the sensitivity lock confirming this finding, referencing D-08.

  Do NOT touch the guidedDemoFlow state machine, the TOUR_PHASES object, or any guided demo
  wiring. The lock for the demo path is correct as-is; this adds a parallel check for the
  normal processing path.
  </action>

  </verify>
  <done>Slide sensitivity buttons are disabled during normal processing; clicking a

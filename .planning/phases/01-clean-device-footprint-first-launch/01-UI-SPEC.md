# Phase 01 — UI Design Contract

> Visual and interaction contract for the honest itemized startup-progress state and the
> new first-run setup checklist. This is an extension of the beta-6 runtime-setup overlay
> (`#runtime-setup-overlay` / `RuntimeSetupGateModel`, `app/ui/app.js:1995-2210`), not a new
> design system and not a new surface. Generated by gsd-ui-researcher, verified by
> gsd-ui-checker.

---

## Scope and Non-Goals

This contract covers exactly two new client states layered onto the existing
`RuntimeSetupGateModel` reducer, both reachable only from the startup sequence:

1. **`checking`** (new) — the honest itemized progress shown while
   `RuntimeBootstrapService.assess()` runs the full validation path on a worker thread,
   behind an already-visible window (D-08/D-09, ROADMAP Success Criterion 3).
2. **`checklist`** (new) — the Ready / Needs Attention first-run checklist shown once,
   before the guided demo can be offered, on any launch where setup has not yet been
   acknowledged (D-12/D-13, ROADMAP Success Criterion 5).

The seven existing reducer states (`gate`, `diagnostics`, `confirm`, `repairing`,
`offline`, `failed`, `ready`) are the accepted, unchanged design contract of
`02-UI-SPEC.md` (`.planning/milestones/v0.9.0-beta.6/phases/02-hard-setup-signed-repair/02-UI-SPEC.md`).
This document does not re-derive them; it cites them and states only the deltas needed to
add `checking`/`checklist` without disturbing them. Where this document is silent on a
token, layout rule, or accessibility rule, `02-UI-SPEC.md` governs.

**Explicitly out of scope for this UI-SPEC** (per the phase's own scope boundary): package
size, the single-instance guard, the taskbar icon, and the updater. None of these has a
UI surface — do not read anything in this document as touching them.

**Non-goals:**
- Do not change beta-5/beta-6 themes, tokens, typography, fonts, radii, shadows, or the
  overlay's modal/focus/inert mechanism.
- Do not add a splash screen, a generic percentage-only bar with no labels, or any
  concealment of the validation delay (explicitly ruled out by the owner, D-09).
- Do not add any affordance in the checklist that implies a download or reinstall of a
  bundled component (D-14) — the checklist is read-only/informational.
- Do not change the existing `repairing` state's phases (Downloading / Verifying /
  Installing safely / Almost there) or its progress semantics — `checking` is a visually
  and semantically **distinct** state from `repairing`. A user must never be able to
  mistake "LecturePack is checking what's already here" for "LecturePack is downloading
  something."

the same visual weight the app already gives a "Paused"/"Interrupted" job badge, not an
alarm.

## Layout and Responsive Contract

Both new states render inside the **same** `#runtime-setup-overlay` scrim/panel used by
the seven existing states (560px ideal width, `max-width:100%`, 2px border, 18px radius,
`var(--shadow-hi)`, `overflow:hidden`, body `overflow-y:auto`) — see `02-UI-SPEC.md`
"Layout and Responsive Contract" for the full, unchanged rule set (820px breakpoint,
16px padding reduction, full-width wrapped actions, 44px minimum hit area, no horizontal
dialog scroll). This document adds only:

- **`checking`:** header unchanged (`Runtime setup` + always-visible `Exit`). Body is a
  vertical list of exactly 5 rows (D-13's items, canonical order supplied by the backend),
  each row = friendly label + a per-row status affordance that is **not** Ready/Needs
  Attention yet (see State Machine below) — plus ONE aggregate progress bar
  (`.lp-fill`, `var(--sunk)` track, `var(--orange)` fill) below the rows, plus one
  `aria-live="polite"` line naming the currently-running check. Exit remains available and
  is the only action (checking cannot be skipped or repaired — it is read-only validation).
- **`checklist`:** header unchanged. Body is the same 5-row vertical list, each row now
  resolved to Ready or Needs Attention, followed by **Continue** (primary, accent) and
  **Skip** (secondary) in the existing action-row pattern (`display:flex;gap:8px;flex-wrap:wrap;margin-top:24px`).
- Below 820px: identical existing rule — rows stack, actions go full-width, `Continue`
  first as the visually primary action.
- Long friendly labels: reuse the exact `renderComponents()` truncation pattern already
  shipped for the failure gate's component rows (`-webkit-line-clamp:2`,
  `overflow-wrap:anywhere`, `title`/`aria-label` carrying the full string) — do not
  invent a new truncation rule for checklist rows.

## Deterministic State Machine

The client reducer (`RuntimeSetupGateModel`) gains two states. `STATES` grows from
`['gate','diagnostics','confirm','repairing','offline','failed','ready']` to include
`checking` and `checklist`. Every existing transition, operation-ID stale-event rule, and
terminal-event rule in `02-UI-SPEC.md` is unchanged; only the entry path into the overlay
changes, from an invisible `bootstrapPending` limbo to a visible `checking` state.

**Full/light path gate (locked, derived from D-07/D-08/D-09 — not re-asked):** `checking`
renders **only** when the backend is running the full validation path
(`_requires_full()` true — cold launch, first-ever launch, or a post-repair
revalidation). On the light/warm path (D-07's one-time-cost logic: subsequent launches
only stat files), no overlay renders at all — the window shows and, if healthy, the app
opens directly, exactly as today. This is the only way to satisfy "cold and warm launch
are architecturally different and must be measured/experienced differently" without
flashing an itemized checklist on every ordinary warm launch.

| Current state | Visible content and permitted actions | Transition |
|---|---|---|
| `checking` (NEW) | 5 rows in canonical backend order, each pending/checking/done (not yet Ready/Needs Attention); one aggregate `.lp-fill` bar (`completed / 5`); one `aria-live="polite"` line naming the active check, e.g. "Checking Whisper runtime…"; **Exit** only | On first canonical bootstrap result for this launch: `runtime_health_state === 'SETUP_REQUIRED'` → `gate` (existing failure gate, entirely unchanged, per D-11). `runtime_health_state === 'HEALTHY'` AND `setup_acknowledged === false` → `checklist`. `runtime_health_state === 'HEALTHY'` AND `setup_acknowledged === true` → close (`setUnderlyingInert(false)`), proceed exactly as today's `admit()` healthy path. |
| `checklist` (NEW) | 5 rows, each resolved Ready or Needs Attention (see Ready-only vs. Mixed below); **Continue** primary; **Skip** secondary; **Exit** removed from this state (**owner-resolved 2026-07-30, Open Question 1** — this is the one place `Exit` is not needed, since the runtime is already healthy and Skip already serves as the low-commitment path) | **Continue** or **Skip** → bridge call persists `setup_acknowledged: true` in `config.json` alongside `runtime_health` (D-16) → close overlay (`setUnderlyingInert(false)`) → identical `syncDemoAdmission()` call already used by the existing healthy path, i.e. the guided-demo offer becomes reachable only now (D-17). |

Existing states `gate`/`diagnostics`/`confirm`/`repairing`/`offline`/`failed`/`ready` and
their transitions, focus targets, and copy are **unchanged** — see `02-UI-SPEC.md`.

**Repair-then-first-healthy interaction (owner-resolved 2026-07-30, Open Question 2 —
confirmed as written below):** the existing
`ready` state (post-repair success, "You're ready") still renders and auto-closes exactly
as today (800ms, or immediately under reduced motion). If `setup_acknowledged` is still
`false` at that point (a first-ever launch that happened to need repair before reaching
HEALTHY), the checklist opens immediately after `ready` closes, keyed by the persisted
flag — not by which path reached HEALTHY. A user only ever sees the checklist once,
regardless of whether their first HEALTHY admission was immediate or repair-recovered.

### Focal Point by New State

| State | Focal point |
|---|---|
| `checking` | The currently-active check's itemized text line and the aggregate bar are focal; no button competes (only secondary `Exit`). |
| `checklist` | **Continue** is the single orange focal action beneath the resolved 5-row list; **Skip** remains secondary and equal in outcome. |

## Ready-only vs. Mixed vs. Failure Gate — the "must not look like an error" contract

This is the direct answer to the constraint that a healthy machine must not see a warning
screen.

**Why a mixed result is even possible while `runtime_health_state === 'HEALTHY'`:** four
of D-13's five items (FFmpeg/ffprobe, Whisper executable+DLLs, bundled model, writable
data directory) are the same hard-blocking components the existing failure gate already
gates entry on — by construction, if the overall state is `HEALTHY`, all four are
already Ready. The fifth item, **supported Windows version**, is a new, non-blocking,
advisory check: an unsupported-but-functional Windows version does not fail admission
(there is no existing gate for it), so it is the only item that can independently render
Needs Attention while the overall runtime stays `HEALTHY`. Per D-14, no checklist row
carries a remediation action — Needs Attention on Windows version is informational only.

| Visual register | Trigger | Treatment |
|---|---|---|
| **Ready-only** (the overwhelmingly common case) | All 5 rows Ready | Calm, positive framing. Heading: "You're ready to go." Every row shows the `success` badge treatment (`.lp-state[data-state="success"]`, green border/soft-fill). No yellow, no orange anywhere except the single Continue CTA. No triangle/warning iconography anywhere in the panel. |
| **Mixed** (Windows-version advisory only) | 4 Ready + 1 Needs Attention (Windows version) | Same calm heading and layout — do **not** switch to a warning heading, warning color scrim, or reordered rows. Only the affected row's own badge changes to the `paused` treatment (`.lp-state[data-state="paused"]`, yellow border/soft-fill) with its one-sentence advisory text. Continue remains the single primary action, fully enabled — mixed is never blocking. |
| **Failure gate** (`gate` state, unchanged) | `runtime_health_state === 'SETUP_REQUIRED'` | Entirely separate, pre-existing visual register per `02-UI-SPEC.md`: "Runtime needs repair" heading, orange **Repair all** primary CTA, no Ready/Needs Attention badges at all — this is a different state the user reaches only via `gate`, never via `checklist`. |

The distinguishing signal for "this is not an error screen" is structural, not just
color: the checklist heading and Continue CTA are **identical between Ready-only and
Mixed** — only a single row's badge differs. The failure gate has a different heading,
different primary CTA label, and different color role for its primary action entirely.

## Startup Progress ("checking") Semantics

- Canonical order and exact 5 labels (backend-supplied identifiers, UI renders the
  friendly label only — backend decides, UI renders, per the established pattern):

  | Backend component id | Friendly label | "checking" live-region text |
  |---|---|---|
  | `windows_version` | Windows version | Checking Windows version… |
  | `ffmpeg_ffprobe` | Media tools (FFmpeg) | Checking FFmpeg & ffprobe… |
  | `whisper_runtime` | Speech engine (Whisper) | Checking Whisper runtime… |
  | `bundled_model` | Speech model | Checking speech model… |
  | `data_directory` | Storage folder | Checking storage folder… |

- Exactly one visual progress bar (the aggregate `.lp-fill`), reusing the identical
  compositor-`scaleX` mechanism as the existing `repairing` state's bar — never a second
  bar, never per-row bars.
- The itemized `aria-live="polite"` line (reuses `runtime-live-polite`, already wired)
  names only the check currently running, per D-09. It must never say anything that could
  read as a download ("Downloading…", "Installing…") — those words belong exclusively to
  the unchanged `repairing` state.
- **Anti-flicker rule (from BUG-20/21/22's lesson: any rapid, backend-driven state flip
  must be deliberately paced, not accidental):** because the whisper-runtime check
  performs a real staged transcription and can legitimately run for several seconds
  (bounded 30s per probe, `runtime_validation.py:24`) while the other four checks resolve
  near-instantly, a row must not flip from pending to done in under 100ms in a way that
  reads as a flash — hold each row's "checking" mark for at least `--motion-normal`
  (160ms) before showing "done", using the existing motion token rather than a new
  one-off duration.
- If the whisper-runtime check is still running past ~5 seconds, append a bounded
  reassurance clause to the live-region text only for that row: "Checking Whisper
  runtime… this can take a few seconds." Do not add a spinner or new animation primitive
  for this — text only, consistent with "no splash screen" and "no new motion tokens."
- `checking` never has a Continue/Skip/Repair action — only `Exit`. There is nothing to
  consent to or decide yet; it is read-only validation, and D-14 forbids any affordance
  suggesting a download at this stage.

## Accessibility and Input Blocking

Identical mechanism to `02-UI-SPEC.md` (non-dismissible modal, `topOverlay()`,
`focusFirst()`, `trapFocus()`, Escape ignored, `inert` on underlying app) applies to
`checking` and `checklist` without modification. This phase adds:

- Initial focus target: `checking` → the `Exit` button (only control present).
  `checklist` → `Continue`.
- `aria-live="polite"` for per-row check-in-progress text (already-established
  `runtime-live-polite` element); `aria-live="assertive"` only for the transition INTO
  `checklist` or `gate` (state change, not per-row chatter) — reuse
  `runtime-live-assertive`, do not add a third live region.
- Each checklist row's Ready/Needs-Attention status must not be conveyed by color alone:
  the visible row text includes the word "Ready" or "Needs Attention" (not just a colored
  border), matching the existing WCAG-driven pattern already used for job-status badges
  elsewhere in the app.
- Reduced motion: `checking`'s per-row status badge (`.lp-state`) and the aggregate bar
  (`.lp-fill`) do **not** go fully instant under `prefers-reduced-motion: reduce` — the
  blanket `.001ms` rule (`app.css:752-757`) is deliberately overridden for exactly these
  classes by the more specific rule at `app.css:809-812`
  (`.lp-state,.lp-stage,.lp-fill{transition-duration:var(--motion-fast) !important;
  transition-property:opacity,background-color,border-color,color !important;}`), so a
  row's opacity/background-color/border-color/color feedback resolves within
  `--motion-fast` (90ms) — perceivable, not merely present, per the comment at
  `app.css:765-776` — rather than truly instantly. `.lp-fill`'s `scaleX` progress value is
  excluded from that transitioned-property list (`app.css:798-800`), so the aggregate
  bar's width **jumps** immediately with no animation while its color still takes 90ms.
  No new reduced-motion carve-out is needed, and none may be added — this phase reuses
  `.lp-fill`/`.lp-state` precisely because their reduced-motion behavior is already
  correct and audited. This directly closes the class of gap BUG-20 found (a rule set
  covering N states needs a reduce override for all N, not the obvious ones) by not
  introducing any new un-audited animated property, and by stating the *actual* existing
  behavior rather than an assumed "instant" that the code does not implement.
- Contrast: `.lp-state[data-state="success"]`/`[data-state="paused"]` and `--on-signal`
  on `--orange` are the exact token pairs already verified AA-compliant under BUG-05's
  fix (green fill 5.91/8.87, yellow-soft as a background only — text stays `--ink`, never
  white-on-yellow). No new color pairing is introduced by this phase, so no new contrast
  audit surface is created — reuse is itself the accessibility guarantee here.

## Open Questions — RESOLVED BY OWNER 2026-07-30

All three were put to the owner during `/gsd-ui-phase 1` and answered. **Each was confirmed
in favour of this document's working assumption**, so no contract text below changes — the
assumptions are now owner decisions and are binding on the planner, not open items.

| # | Question | Owner decision |
|---|----------|----------------|
| 1 | `Exit` affordance on `checklist`? | **No Exit.** Omit from `checklist` only; keep it everywhere else including `checking`. |
| 2 | Show the checklist after a repair-recovered first-ever-healthy admission? | **Yes, show it.** Flag-keyed design as written stands: the checklist is keyed to `setup_acknowledged` (D-16), not to which path reached `HEALTHY`. Decisive reason: the checklist is the gateway to the demo offer (D-17), so skipping it post-repair would silently drop the demo offer for exactly the users who had the roughest install. |
| 3 | Is `Continue` vs. `Skip` a real behavioral distinction? | **Identical in effect, different label.** Both persist `setup_acknowledged: true` and proceed to demo-offer sync. This is the literal reading of D-17. |

The original question text is retained below for the reasoning behind each recommendation.

---

1. **Does the `checklist` state need its own `Exit` affordance?** Every other reducer
   state in this overlay (including the newly added `checking`) always shows `Exit`. This
   document's working assumption is that `checklist` legitimately omits it, because by the
   time `checklist` renders the runtime is already `HEALTHY` — there is nothing to protect
   the user from by exiting, and forcing a visible Exit next to Continue/Skip would add a
   third, redundant action to the one state in this whole overlay where the app is
   provably fine. Recommended resolution: omit Exit from `checklist` only; keep it
   everywhere else including `checking`. **If the owner disagrees, add Exit back as a
   tertiary action, same visual weight as Skip.**
2. **Does a repair-recovered first-ever-healthy admission need to show the checklist
   immediately after the existing `ready` ("You're ready") success state closes?**
   CONTEXT.md's D-12 is framed around "first-ever launch" in general, but D-17's demo-gate
   condition and the existing `ready` auto-close (800ms) were designed before this
   checklist existed. This document's working assumption: yes — the checklist is keyed
   purely to the persisted `setup_acknowledged` flag (D-16), not to which path reached
   `HEALTHY`, so a user's first-ever healthy admission always shows the checklist exactly
   once, whether that admission came from a clean pass or a successful repair.
   **Recommended resolution: proceed with the flag-keyed design as written above.** If the
   owner instead wants a successful repair to implicitly count as "setup already
   acknowledged" (skip the checklist post-repair), that changes the backend's
   `setup_acknowledged` write timing, not this document's visual contract.
3. **Is "Continue" vs. "Skip" a meaningful behavioral distinction, or two labels for the
   identical action?** D-12 only names "Continue"; D-17 separately says the demo is
   offered "after the user continues past the checklist **or** deliberately skips it,"
   which reads as if skip is a distinct path. Since the checklist is non-blocking and
   D-14 forbids any remediation affordance either way, this document's working assumption
   is that **Continue and Skip have byte-identical effects** (both persist
   `setup_acknowledged: true` and proceed to demo-offer sync) and differ only in label —
   Continue for a user who reviewed the list, Skip for one who does not want to. **If the
   owner intends a real behavioral difference (e.g., Skip suppresses the demo offer for
   this session while Continue does not), that changes D-17's demo-gate condition and
   needs to be resolved before planning, not inferred by this document.**

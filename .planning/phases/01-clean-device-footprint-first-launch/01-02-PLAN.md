<objective>
Restore installer-asset publication to the release workflow, additively, so the in-app updater can
consume a release again — and add the test that stops the regression from recurring silently.

This implements **D-22**, the owner decision recorded during planning: the `<updater_regression>`
discovered while verifying the size question is resolved *inside this phase*, not deferred. Commit
`a6164b1` ("feat(02-05): automate signed runtime release assets") replaced the installer-publishing
job with one that publishes only six signed runtime component assets. `expected_asset_names()`
(`app/desktop/update_service.py:117-120`) requires `Setup.exe` (or `Portable.zip`) plus
`SHA256SUMS.txt`, so `select_asset()` raises against every release the current workflow produces.

D-22 is explicit that this is an **add-back, never a re-swap**: the six signed runtime component
assets stay exactly as they are, and nothing about the AD-19 signed-manifest repair contract may
weaken. Until this lands, this phase may not claim "beta-6 updater behavior preserved" — that claim
is tied to D-22 and lives in this plan's `must_haves`.

A second, unlisted silent-failure path is closed here too: `build.py`'s installer branch prints a
WARNING and returns early when ISCC is not found, so a runner without Inno Setup would produce no
`Setup.exe` and no error. The restored `choco install innosetup` step plus a pre-publish existence
assertion close that.

Purpose: make the updater consumable again without touching the repair path.
Output: a workflow that publishes nine assets (six signed + three installer/updater), and a contract
test derived from `expected_asset_names()`.
</objective>

| GitHub release assets → user machine | The in-app updater downloads a published asset and verifies it against `SHA256SUMS.txt` before installing. Anything published here crosses onto user machines. |

## 1. What this project is

LecturePack is a Windows desktop app (PySide6 / Qt WebEngine) that turns recorded
lectures into slides, transcripts, and study material. The UI is a single-page
HTML/CSS/JS app (`app/ui/`) rendered inside a `QWebEngineView` and driven by a
`bridge.js` ↔ Python signal layer. It is NOT a web app with a server — everything
in `app/ui/` is static, loaded from disk, and talks to the desktop process only.

## 3. Design identity — what the UI *is*

**Refined neobrutalist.** This is the load-bearing design fact of the whole
project; every decision below is downstream of it.

- **~112 solid `2px`/`1.5px` borders** carry the visual weight — not shadows, not
  color. This is why every motion decision in §4 protects border crispness above
  almost everything else.
- **Flat fills, no gradients** (one deliberate exception: a striped
  `repeating-linear-gradient` progress-bar texture, animated via
  `background-position`, pre-existing and out of scope).
- **Bold, geometric type**: Space Grotesk for UI chrome/buttons/nav, JetBrains
  Mono for numeric/technical readouts (timers, percentages, file sizes). Never
  mixed within a component.
- **Fixed palette**, two themes (light/dark) via `[data-theme]` CSS custom
  properties — `--bg/--panel/--ink/--muted/--border/--line`, signal colors
  `--orange/--blue/--green/--red/--yellow` each with a `-soft`/`-ink` variant for
  WCAG-safe text-on-fill pairs. This pass added **zero new colors** — every new
  rule reuses existing tokens, including the new hard-shadow tokens (see §4.1),
  which are built from `var(--border)`.
- **Cards** (`.lp-card`) are the primary content unit: `2px` border, flat panel
  fill, no radius exaggeration.

None of the above changed this session. The mandate was explicitly motion-only,
and it held.

## 4. What this session did — the motion system

### 4.1 Token layer (`app/ui/app.css`)

Three duration tokens, retuned in place from their beta.4 values:

| Token | Before | Now | Use |
|---|---|---|---|
| `--motion-fast` | 120ms | **90ms** | hover/press feedback — fires hundreds of times/session |
| `--motion-normal` (new; `--motion-medium` kept as alias, ~40 rules reference it) | 180ms | **160ms** | the default: state changes, entrances, reveals |
| `--motion-slow` | 240ms | **220ms** | the largest move allowed anywhere: progress, reorder, completion |

Easing, four tokens now (one added):

- `--motion-ease: cubic-bezier(.22,1,.36,1)` — decisive ease-out, for **movement**
  (translate/scale). Unchanged.
- `--motion-ease-in: cubic-bezier(.55,0,1,.45)` — exits only. Unchanged.
- `--motion-spring: cubic-bezier(.2,0,0,1)` — critically-damped, no overshoot, for
  state changes (icon/badge flips). Unchanged. This is the project's deliberate
  substitute for real spring physics — chosen specifically to avoid the
  "bouncy/toy-like" read the user's brief banned.
- **`--motion-ease-soft: cubic-bezier(.33,0,.2,1)` — new.** Added mid-session in
  direct response to user feedback (§4.4). Carries **opacity only**, never
  transform. See §4.4 for why this token exists at all.

New shadow tokens, in both light and dark theme blocks:
`--shadow-hard: 3px 3px 0 var(--border)`, `--shadow-hard-sm: 2px 2px 0
var(--border)`. These are the only genuinely new visual element introduced —
see §4.6 for why, and the honest caveat about scope.

**Property discipline**: every new rule animates only `transform`, `opacity`,
`background-color`, `border-color`, `box-shadow` — per the user's brief. Nothing
new animates `width`/`height`/`top`/`left`/`margin`/`padding`/`filter`. (Two
pre-existing violations were found and left alone as out of scope — see §7.)

### 4.2 The reusable class set

One "MOTION SYSTEM v1" block in `app.css`, ~19 classes, no per-screen bespoke
animations. This was a hard requirement from the brief ("a small set of reusable
classes rather than separate animations for every screen") and held throughout —
nothing in this pass invented a one-off keyframe for a single component.

| Class | What it's for |
|---|---|
| `.lp-anim-in` / `.lp-anim-in-fast` | generic fade+rise entrance, two speeds |
| `.lp-anim-fade` | **pure opacity crossfade, zero movement** — added for tab panes, see §4.4 |
| `.lp-stagger>*` | staggered list entrance, capped at ~210ms total delay so long lists don't crawl |
| `.lp-lift` | card hover-lift; aliases the pre-existing `.lp-card` rule rather than duplicating it |
| `.lp-press` / `.lp-press-sm` | **the physical button press** — hard shadow collapses to flat on `:active`, translate compensates. See §4.6. |
| `.lp-nav-ind` / `.lp-nav-list` | sliding sidebar active-indicator, positioned via `--ind-y`/`--ind-h` custom properties set by JS |
| `.lp-fill` / `.lp-bar-w` | progress bar fill (scaleX-based / width-based) |
| `.lp-stage` / `.lp-state` | processing-stage rows and job/export state cards, driven by a `data-state` attribute: `idle|running|paused|success|failed|interrupted|complete` |
| `.lp-scrim` / `.lp-pop` | modal backdrop + panel entrance (and `.out` variants for exit) |
| `.lp-tip` | tooltip entrance (e.g. timeline scrub preview) |
| `.lp-toast` | notification entrance — opacity-only, see §4.7 |
| `.lp-reveal` | completion-panel reveal, staggers its own children |
| `.lp-flip` | FLIP-pattern reorder transition (implemented, currently unused — see §4.8) |
| `.lp-out` | generic exit fade, used by the modal-close helper |

Two classes from an earlier iteration (`.lp-skel`, `.lp-data-in`, `.lp-menu`)
were **deleted** before this pass finished — no genuinely slow async render was
ever found to justify a skeleton, and the app has no dropdown menus. Dead CSS
was treated as a defect, not shipped speculatively.

### 4.3 Screen navigation

- `setScreen()` (app.js) now wraps its DOM mutation in `LP.motion.nav(fn)`, which
  calls `document.startViewTransition(fn)` when available and not
  `prefers-reduced-motion`, else falls back to calling `fn()` directly with a
  try/catch around the View Transition call so navigation can never be lost.
- **Confirmed live in the real Qt WebEngine**: `typeof
  document.startViewTransition === 'function'` (§5). A `html.lp-vt` class gates
  a root-only cross-fade layer (`::view-transition-old/new(root)`); no per-element
  `view-transition-name` is set — the scope is deliberately just the root
  cross-fade, not per-element shared-element transitions.
- Per-section inline `animation:lpin .3s ease` attributes were **removed** from
  all 7 `<section data-screen>` elements in `index.html` — inline style was
  outranking the stylesheet's screen-transition rule by specificity, so screens
  were previously hard-cutting despite a CSS rule existing to prevent it. This
  was the single highest-value single-line fix in the whole pass.
- The sidebar gets a `.lp-nav-ind` sliding indicator — a `3px` rail whose
  `transform:translateY()` and `height` are set by `LP.motion.indicator()`
  reading the active nav button's `offsetTop`/`offsetHeight`. Verified moving in
  the live app (§5).

### 4.4 The user's mid-session correction: tab switching felt like a "bounce or flash"

This is worth documenting in detail because it's the one piece of direct design
feedback in this pass, and the fix generalizes.

**Diagnosis**: two compounding causes.
1. Entrances animated `opacity` from `0` — a fully-invisible-to-visible pop reads
   as a flash regardless of duration.
2. `--motion-ease` (the project's one existing "movement" curve,
   `cubic-bezier(.22,1,.36,1)`) is a near-exponential ease-out: it resolves
   ~80% of its total change in the first third of its duration. That's correct
   for a card sliding 2-4px, imperceptible at that distance — but wrong for
   *opacity*, where the eye is far more sensitive to the front-loaded change and
   reads it as a snap.

**Fix, in two parts**:
- New entrance keyframes start from `opacity:.35`, not `0` — landing partly
  visible removes the flash while the transition stays perceptible.
- Opacity and transform were split into **two stacked animations** so each can
  carry its own easing curve (CSS cannot vary easing per-property within one
  `@keyframes` block): opacity now uses `--motion-ease-soft` (gentle in-out,
  no front-loading), while transform keeps `--motion-ease`.
- **Tab panes specifically** (Study screen's Ask/Quiz/Flashcards/Notes) were
  moved off the fade+rise combo entirely onto `.lp-anim-fade` — a **pure
  opacity crossfade with zero movement**. A pane sliding inside a stationary
  card was the actual source of the "bounce" read; removing the motion
  component (not just softening it) was the right fix, not a compromise.

**Verified visually** in the delivered before/after video (§5): the tab-switch
scene shows a clean, legible crossfade with no flash in either the light or dark
build. This was independently confirmed by the recording agent's frame-by-frame
read, not just claimed.

### 4.5 Reduced motion

Extends the existing `@media (prefers-reduced-motion: reduce)` block. Every new
class is neutralized: `animation:none !important` (safe now that every entrance
lands at `opacity:.35`→resolved rather than `0`), `transform:none !important` on
lift/press/nav-indicator, color/background/border transitions **kept** (clamped
to `--motion-fast`) because color feedback is information, not decoration.
`.lp-flip` and `.lp-nav-ind` get `transition:none` specifically rather than a
blanket duration clamp, so a reduced-motion user's sidebar indicator jumps
instantly rather than crawling at 0.001ms (which is technically "off" but still
paints an intermediate frame on some compositors).

**Verified genuinely engaging in Qt** (§5): frame counts during a reduced-motion
recording pass dropped from ~147 to ~6 for the same navigation sequence,
confirming animations actually stopped rather than merely looking similar.

### 4.6 The physical press — and a real defect caught and fixed

`.lp-press`/`.lp-press-sm` is the pass's centerpiece: a hard offset shadow
(`--shadow-hard`) that **collapses to flat** on `:active` while the button
translates toward the shadow's origin — the button reads as physically pressed
into the surface rather than merely darkening. This deliberately avoids
`scale(0.96)`, the conventional press affordance: scaling a 2px-bordered slab
resamples the border to a fractional pixel width and visibly softens it, which
is exactly the weight this UI depends on (a decision the beta.4 session had
already made for the plain `translateY(1px)` press; this pass extends the same
reasoning to the new hard-shadow variant).

**Defect found by independent review, then fixed**: 14 of the 20 buttons given
`.lp-press`/`.lp-press-sm` carried an **inline `box-shadow`** in their markup
(mostly `var(--shadow-soft)`, one custom `rgba` shadow on the "export all"
button). An inline style always outranks a class selector by specificity — so
the class's resting shadow, hover lift, and, critically, its `:active` collapse
were **completely inert** on those 14 buttons; only the small `translate()` half
was rendering. This was caught by a dedicated adversarial review pass (not by
the agent that wrote the markup) and fixed by removing only the conflicting
inline `box-shadow:` declaration from each button, leaving every other inline
declaration byte-identical. A follow-up design pass then checked each of the 14
individually for layout collisions (tight rows, edge-to-edge bars, dark inset
panels) before confirming the hard shadow was safe everywhere it landed — none
were demoted.

**Honest scope note**: the brief listed "hard offset shadows" under things to
*preserve*, but no hard shadow existed anywhere in the beta.4 UI before this
session — every existing shadow was soft/blurred (`--shadow-soft`,
`--shadow-hi`). This pass **introduced** hard shadows, scoped to the 20 primary
action buttons carrying `.lp-press`/`.lp-press-sm`, and did not touch
`--shadow-soft`/`--shadow-hi` or apply hard shadows anywhere else (cards, panels,
modals all keep their existing soft shadows). If the intent was that hard
shadows should already have existed and needed no introduction, that's a premise
worth revisiting with the user — but as executed, it was treated as a new,
narrowly-scoped addition consistent with "refined neobrutalist," not a
restoration.

### 4.7 Notifications, modals, tooltips

- Modals (`#onb-overlay`, `#whatsnew-overlay`, and the JS-built `lpModal`) now
  have a real **exit** animation, not just an entrance — previously they closed
  via instant `hidden=true`/`.remove()` despite having an entrance animation,
  which was flagged as the single highest-severity abrupt-state finding in the
  pre-work inventory. `LP.motion.close(el, done)` adds `.out`, waits for
  `animationend` (with a 300ms fallback timeout so a modal can never fail to
  close), then runs the real close/removal callback. Guarded against
  double-invocation.
- The toast/notification singleton (`#lp-toast`) took two attempts to wire
  correctly. First attempt: apply the existing slide-in keyframe
  (`translateX(16px)→...`) — rejected before shipping, because the toast's
  inline `cssText` already sets `transform:translateX(-50%)` for horizontal
  centering, and the keyframe's implicit `to` state would have been the
  element's own cascaded transform, visibly yanking the toast off-center on
  every show. Fixed by making the toast entrance **opacity-only**
  (`.lp-toast{animation:lpfade ...}`), which cannot conflict with any transform
  the element carries, on the reasoning that "a toast that slides is decoration,
  a toast that fades is information" — consistent with the reduced-motion
  philosophy applied elsewhere.
- Tooltip (`#scrub-preview`, the timeline scrub-preview) gets `.lp-tip`, a fast
  fade-in.

### 4.8 What was deliberately NOT done

- **Queue reorder does not use the FLIP pattern**, despite `LP.motion.flip()`
  being fully implemented (measure→mutate→invert→play, reduced-motion-aware,
  currently has no caller). `renderQueue()` rebuilds the list via wholesale
  `innerHTML` replacement, so old and new row elements are never the same DOM
  nodes — FLIP has nothing to measure a delta against. New rows instead get
  `.lp-anim-in`. Making FLIP actually apply would require restructuring how the
  queue renders (incremental DOM patching instead of full replacement), which is
  a real architecture change, not a motion change, and was explicitly out of
  scope ("changing application behavior" was banned by the brief).
- **No skeleton/loading states were added anywhere.** The brief said to add them
  "only where data genuinely takes time to load"; no such case was found in this
  app's async surfaces. Shipping one speculatively was judged worse than
  shipping none.
- **Processing progress, pause/resume, completion reveal, and queue reorder are
  implemented but not yet demonstrated on video** with a real backend job — see
  §6.

- **Two pre-existing violations of the "no bounce, nothing over 220ms" motion

  one intentional "big moment" transition in the app is a design call, not a
  cleanup, and doing it silently inside a motion-system PR would be scope creep.
- **A recording-tooling gotcha, worth knowing if this needs to be redone**: OS-
  level window capture (`ffmpeg -f gdigrab`) is **not reliable against Qt
  WebEngine**. It twice failed silently during this session — once capturing an
  unrelated window in the same screen rect, once freezing on a stale frame
  while the actual DOM kept updating (verified via `Runtime.evaluate` showing
  live state changes the recording never reflected). Root cause: QtWebEngine's
  GPU-composited swap chain doesn't round-trip through the GDI surface gdigrab
  reads. **Fix that worked**: CDP `Page.startScreencast`, which reads the
  compositor output directly and needed no OS-level window focus at all.
- The `--shadow-hard` introduction (§4.6) is a genuinely new visual element, not
  purely a motion change. Flagging again here because it's the one place this
  session's scope could be read as having expanded beyond "motion-only," and the
  user should have the chance to object before it's committed.

## 9. Skills-folder retrospective — PROMOTE TO SKILLS FOLDER

The Claude Skills folder (`…\ECO182\Claude share\Claude share\`) was
**unreadable again this session** — same gotcha as recorded in the prior
handoff. Recording the candidate lessons here verbatim per the handoff skill's
instructions, since they could not be written to the folder directly:

1. **Opacity and movement need different easing curves, and a single ease-out
   curve tuned for a small transform reads as a "flash" when reused for
   opacity.** A front-loaded ease-out (most of the change in the first third of
   the duration) is imperceptible on a 2-4px translate but reads as a snap on
   opacity, because the eye is far more sensitive to luminance change than
   position change at that magnitude. Fix: a separate, gentler in-out curve for
   opacity (`cubic-bezier(.33,0,.2,1)` worked here), and start entrance opacity
   from a partly-visible value (e.g. `.35`, not `0`) rather than fully invisible.
   Generalizable to any UI with fade+move combined entrances.
2. **A press/hover effect defined as a CSS class is silently inert on any
   element carrying the same property inline** — inline styles always win by
   specificity regardless of pseudo-class state, so a button with an inline
   `box-shadow` will never show a class-based `:active` shadow-collapse, with no
   console warning and no visual signal that anything is wrong except "the
   press doesn't look like it did in the design." This is the same failure
   shape as a previously-logged lesson about hardcoded mirror lists — always
   grep for inline instances of every property a new utility class touches
   before assuming the class controls that property everywhere it's applied.
3. **OS-level screen/window capture (gdigrab, and likely most BitBlt-based
   tools) cannot be trusted against GPU-compositor-backed views like
   QtWebEngine** — it can silently capture the wrong window (same screen rect,
   different window) or freeze on a stale frame while the real content
   continues to update, with no error thrown either way. For any Qt WebEngine
   (or likely Electron/CEF) recording task, use the browser engine's own
   protocol-level screencast (CDP `Page.startScreencast` for Chromium-based
   engines) instead of OS-level screen capture.
4. **A synthetic DOM `.click()` does not trigger `:active` styling.** Verifying
   or recording a CSS `:active`/press state requires real input-level events
   (CDP `Input.dispatchMouseEvent` mousePressed/mouseReleased, or equivalent) —
   a `click()` call will silently produce a "press" recording that shows no
   press at all.
